# Decision: Self-Update via GitHub Release Archive, Not Git or GitPython

Version: 0.1.0
Status: Draft
Style Guide: style-guide--versioned-documents-in-unrendered-markdown

## Context

`install-restic.py` currently requires a `git clone` of `osat-fluent-restic-tool` to obtain the installer itself; `git` is a stated requirement in the tool's documentation. Separately, the manager has no mechanism to update itself — only `--install`, `--switch`, `--status`, and `--remove` for the restic binary it manages. We wanted a self-update path for the manager script, and a simpler first-run acquisition story that does not require `git`.

## Decision

Self-update, and the initial bootstrap acquisition of the installer itself, will use the tool's own archetype 5 acquisition pattern, retargeted at the manager's own source instead of the restic binary: download the tagged source archive from GitHub (`codeload.github.com/<owner>/<repo>/tar.gz/refs/tags/<tag>`), verify it against a project-published `SHA256SUMS`, extract it, and install it into a versioned directory alongside the existing restic-binary install roots (for example `~/.local/share/restic-tool/manager/<version>/`), using the same archive-first resolution, health check, and refuse-and-remove behavior `acquire_binary()` and `binary_ok()` already implement. Activation follows the same env-file-pointer pattern `restic-tool.env` already uses for the active restic version.

`git` stops being a runtime or install-time requirement entirely. It remains useful only to people cloning the repository to develop the tool, not to people installing or updating it.

## Alternatives considered

**Git clone, then `git fetch` / `git checkout` for self-update.** Reuses the git requirement already stated in the docs, and gets integrity for free from git's own content-addressing rather than inventing new checksum machinery for the script. We did not choose this because it turns `git` from a one-time bootstrap dependency into a permanent runtime dependency for every future update, and it raises a platform-availability question this decision otherwise avoids: git is not built into Windows the way it effectively is on macOS and Linux. We confirmed Git for Windows publishes checksummed, portable `MinGit-<version>-<arch>.zip` release assets that would fit this project's archetype 5 pattern cleanly, but no comparable official static git binary exists for Linux or macOS — managing git consistently across platforms is its own, asymmetric problem, not a fit for something as core as self-update. A git working tree also has its own partial-update and dirty-tree failure modes that the existing versioned-directory pattern avoids by construction.

**GitPython.** Considered as a friendlier API over git, but rejected on two grounds. It is a PyPI package with transitive dependencies (`gitdb`, `smmap`), which conflicts with the standing rule, stated in `install-restic.py`'s own docstring and in the archetype 5 spec template, that Fluent installers use Python 3.8+ and the standard library only. And it does not remove the underlying git-availability dependency — every call shells out to the same `git` binary — so it inherits the first alternative's problems while adding a packaging dependency on top.

**Downloading the tagged release archive (chosen).** Reuses acquisition machinery already proven against the restic binary, requires no `git` at install or update time, and produces a single artifact the existing archive-first, versioned-directory, health-check pattern already knows how to manage. The one gap relative to restic's own binary acquisition is that no upstream maintainer publishes a checksum for our own tag's source archive; GitHub's autogenerated tarball bytes are also not guaranteed stable across GitHub's own internal changes over time. We close this by publishing our own `SHA256SUMS` at tag time, in the same step where `bump-version.py --release` already runs, so self-update never trusts an unverified download — consistent with the "no claim without a verification behind it" rule already applied to restic's own acquisition.

## Consequences and follow-on work

- Once implemented, the `git` requirement can be dropped from `install-restic.py`'s Requirements section, the backup guide, and the installer-tests document, all of which currently list it.
- The release workflow (`commit-and-versioning-workflow`) needs a checksum-publishing step added at tag time, so a `SHA256SUMS` for the source archive always exists for self-update to verify against.
- The manager's on-disk layout gains a versioned subtree for its own source (for example `~/.local/share/restic-tool/manager/<version>/`) alongside the existing restic-binary directories. `--status` should likely report the manager's own version and update state the same way it already reports restic's.
- The `osat-fluent-git-tool` idea raised during this discussion is decoupled from this decision. It may still be worth building, for users who want consistently managed git across operating systems, but it is no longer a prerequisite for restic-tool's self-update.
- This is a candidate for generalization into the `osat-fluent` governance repository, as an addendum to the archetype 5 specification, once it has been implemented and exercised here — consistent with this project's existing practice of proving a pattern in the tool that needs it before promoting it to governance.
